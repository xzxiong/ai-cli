# Scope 模式 — 缩小实现方案 Checklist

在完成 Issue/PR 拉取后使用本清单生成报告。全程围绕「核心目标 → 关键成果 → 收敛 diff」。

## 报告结构

```markdown
# Scope Review: <PR title>

PR 基础信息
- **模式**: 🎯 Scope Review（缩小实现方案）
- **PR**: <url> (`#N`)
- **Issue**: <#M title> 或 `⚠️ 未关联 Issue`
- **范围置信度**: 高（有 Issue 验收口径）/ 中 / 低（仅 PR 自述）

## 〇、总结（TL;DR）
- 一句话：目标是什么、实现是否偏胖
- 🔴 / 🟡 / 🟢 数量
- **收敛建议**：
  - **可维持现状** — 无 🔴，改动均锚在关键成果上
  - **建议收敛后合并** — 有 🔴/较多 🟡，按删改清单瘦身
  - **范围需重切** — 目标不清或实现与 Issue 明显两张皮

## 一、核心目标
1. …
2. …
（1～3 条；写交付意图，不写实现手段）

## 二、关键成果与 Non-goals
### 关键成果
- 目标 1 → 成果 A / B
- 目标 2 → 成果 C
### Non-goals（本 PR 不应顺带完成）
- …

## 三、范围对照（diff → 成果）
按改动块说明：保留 / 收敛 / 删除候选。测试文件单独说明是否在锁成果。

## 四、建议删改清单
| ID | 级别 | 位置 | 建议动作 | 关联目标/成果 | 理由 |
|----|------|------|----------|---------------|------|
| I-1 | 🔴 | … | … | … | … |

### Keep（勿误删）
- …

## 五、专项扫描摘要
用短句勾过；未命中写「未发现」：
- 等效冗余：
- 过度封装：
- 多余加解密/混淆：
- 过度防御：
- 非必要幂等：
- 过分设计（相对成果）：

## 六、测试与成果锁
- 哪些测试直接锁关键成果（应保留，可建议再补边界）
- 哪些测试只锁内部封装形状（可改写或删除）
- **不要**因为测试多就判过度设计
```

## 目标提取提示

从 Issue / PR 中优先抓：

- 复现步骤与期望行为
- Acceptance / 验收 / Success criteria
- 「不在范围内」「Won't do」「Out of scope」
- 失败现象（OOM、wrong result、crash）——成果常是「该现象消失且可回归」

忽略：

- 无验收绑定的 refactor 冲动
- 「顺便统一一下 XX」且 XX 与故障无关

## 收敛判定启发式

**偏胖信号（倾向 🟡/🔴）**

- 新增 package / 通用 framework，但调用方只有一处
- interface 仅一个生产实现 + 测试 mock（且生产路径可直接测）
- 引入幂等键/去重表，但 Issue 是确定性单次写修复
- 引入 encrypt/sign/secret 流转，但 Issue 未提安全/合规
- 同一不变式校验三次（入口、service、DAO 各一次）而无分层理由
- Feature flag 矩阵超过成果需要的开关数

**应保留信号**

- 回归测试、边界 case、fault injection 测试对准成果
- 为满足成果所必需的最小 API/错误码改动
- Issue 明文要求的兼容或开关

## 与 review-pr 的边界

| 问题类型 | 谁主审 |
|----------|--------|
| 是否做多了 / 能否更短 | **本 skill** |
| 逻辑 bug / 安全 / 性能 / CI | `review-pr` |
| 两者都要 | 先本 skill 收敛范围，或先 `review-pr` 再本 skill 二过 |

发现阻塞级正确性 bug 时，可在 TL;DR 提一句并建议转 `review-pr`，但不要把本报告写成完整 Code Review。
