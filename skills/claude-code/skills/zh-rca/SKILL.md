# 中文根因分析（zh-rca）

用中文做可验证的因果推理。目标不是堆术语，而是把「看到了什么」推到「最可能是什么、怎么证明」。

## 何时使用

- 用户要分析异常、故障、性能、偶现问题、业务现象
- 用户问「为什么」「根因是什么」「怎么排查」
- 已有日志/报错/现象描述，需要结构化推理
- 需要写复盘、故障结论、验证计划

若问题已明确属于某个专用技能（如 GitHub issue 全流程用 `issue-analyzer`，解析流水线性能用 `log-perf-analyze`），先走专用技能；本技能负责其之上/之外的中文因果推理与结论组织。专用技能产出证据后，仍可用本技能把结论整理成「现象→原因→证据→验证」。

## 工作原则

1. **先现象，后原因** — 不要一上来就下结论。把可观察事实写清楚，再推理。
2. **区分事实与推断** — 事实来自日志、指标、代码、复现步骤；推断要标置信度。
3. **多因并列，排序不独断** — 至少给 2–3 个候选原因（除非证据已充分到几乎唯一），按置信度排序。
4. **每个原因都要可证伪** — 写清「若成立应看到什么 / 若不成立应看到什么」。
5. **验证优先于长篇解释** — 下一步动作要具体、可执行、能缩小假设空间。
6. **全程中文输出** — 专有名词、命令、路径、错误原文可保留英文/原文，解释用中文。

## 分析流程

### 1. 澄清现象（Observation）

从用户描述与已有材料中提取：

| 维度 | 要回答的问题 |
|------|-------------|
| 是什么 | 具体表现（错误文案、卡死、变慢、数据不对…） |
| 何时 | 开始时间、是否持续、是否周期性 |
| 何处 | 环境 / 服务 / 接口 / 租户 / 版本 |
| 范围 | 全量还是局部；影响面多大 |
| 变化 | 最近是否有发布、配置、流量、依赖变更 |
| 已排除 | 用户或前人已经试过并排除了什么 |

信息不足时，先基于现有材料给出**带假设的初步分析**，并明确列出缺口；不要空等完整信息。

### 2. 建立因果假设（Hypotheses）

对每个候选原因写：

- **机制**：它如何导致观察到的现象（因果链，尽量短）
- **置信度**：高 / 中 / 低（或百分比），并说明依据
- **支持证据**：已有哪些事实支持
- **反对证据**：哪些事实不支持或尚未检查
- **验证方法**：最小成本的下一步（查哪条日志、比哪个指标、跑哪个命令、看哪段代码）

优先考虑这些常见类别（按场景取舍，不必全写）：

- 变更引入（发布、配置、开关、依赖版本）
- 资源/容量（CPU、内存、FD、连接池、队列积压）
- 依赖故障或退化（下游超时、限流、抖动）
- 并发/竞态/重试放大
- 数据/状态异常（脏数据、缓存不一致、迁移残留）
- 观测偏差（看错窗口、看错实例、指标桶失真）

### 3. 收敛与排序

- 用现有证据淘汰明显不成立的假设
- 把剩余假设按「解释力 × 证据强度 / 验证成本」排序
- 明确当前**最可能根因**与**仍不确定点**

### 4. 给出验证与处置

验证步骤要：

- 可独立执行（命令、查询、对比点写清楚）
- 能区分假设（成功/失败分别意味着什么）
- 先便宜后昂贵（先日志/指标，再复现/改代码）

若已有足够证据，可直接给修复建议；但仍要保留「如何确认修复有效」的验证点。

## 输出模板（必须使用）

默认用下面结构。短问题可压缩段落，但四个板块标题保留。

```markdown
## 现象
- ...
- （时间 / 环境 / 范围 / 变更点，有则写）

## 可能原因（按置信度排序）
1. **[高/中/低] 原因标题**
   - 机制：...
   - 支持：...
   - 不支持/待查：...
2. **[...] ...**
3. **[...] ...**

## 证据
- 已确认：...
- 仍缺：...

## 下一步验证
1. ... → 若成立则 ...；若不成立则 ...
2. ...
3. ...

## 当前结论
一句话：最可能是 X，因为 Y；下一步先做 Z。
```

可选附加（有需要再加，避免喧宾夺主）：

- **影响面**：谁受影响、是否仍在发生
- **临时缓解**：在根因未修前可做什么
- **长期修复**：代码/配置/流程改动建议

## 推理时注意

- **不要把相关当成因果**：同时出现 ≠ 互为因果。
- **不要忽略「最近变更」**：但也不要默认「都是发布导致」。
- **偶现问题**：优先查重试、超时、限流、负载尖刺、特定输入。
- **性能问题**：先定基线与瓶颈阶段，再谈优化；避免未测量就给方案。
- **多服务链路**：按时间线对齐（请求 ID / trace / 文件 ID），写清哪一跳开始异常。
- **与专用技能协作**：需要拉 issue、查 k8s、做解析流水线 timing 时，调用对应技能或复用其流程，再回到本模板输出中文结论。

## 反例（避免）

- 只有结论没有现象拆解
- 只列很多可能原因，没有置信度与验证
- 验证步骤模糊（「再看看日志」）
- 中英混杂的长篇叙述淹没因果链
- 在证据不足时假装已经确定唯一根因

## 简例

**用户**：prod 上某个接口从昨天开始偶发 30s 超时，重启后好一会儿又出现。

**期望风格（摘要）**：

- 现象：昨日起偶发 30s 超时；重启短暂缓解；需补环境/接口/时间窗
- 原因候选：下游连接池耗尽（高）；依赖限流/超时对齐成 30s（中）；某实例内存泄漏导致 Full GC（中）等
- 证据：重启缓解支持连接/内存类；固定 30s 支持超时配置对齐
- 验证：先看该接口 p99 与下游超时配置、连接池指标、超时瞬间的实例与 GC 日志
