# Feature Interface Flow

用**抽象接口**把 feature 的交互边界钉死，再用 **MVP 白话路径 + 边界场景** 驱动
测试与实现。测试不是实现的附属品：每个测试要能说清它在保护哪条契约；没有人工
可判定意义的 UT 不要写。

## 何时启动

用户要「从需求走到可验收实现」，或明确要求接口优先 / Mock 优先 / MVP 测试设计。
若任务其实是单点 bugfix 且不引入新交互面，改走排障/修复 skill，不要硬套本流程。

## 阶段总览（严格顺序）

```text
Check → Design → Impl → Test → Review → 验收
```

| 阶段 | 产出 | 退出条件 |
|------|------|----------|
| **Check** | 相关 skill/规则盘点、可复用模式、非目标 | 知道跟谁对齐、不重复造轮子 |
| **Design** | 需求摘要、接口文件、MVP 白话路径、边界场景表 | 用户确认接口与 MVP（或明确授权直接实现） |
| **Impl** | Mock 测试 → 正式实现 → Gate | 接口稳定；Mock 绿；实现通过契约测试与 gate |
| **Test** | MVP case 完整表述 + 边界扩展 + 每个测试的「测试意义」 | 读者不看实现也能理解测了什么、为何测 |
| **Review** | 接口契约审查、Mock 覆盖、Gate 结果 | 无阻塞契约缺口 |
| **验收** | 接口测试 × Gate × Test 叙述三联通过 | 可合并/可演示 |

阶段可在同一会话内连续推进；**不得跳过 Design 的接口落盘直接写业务实现**
（除非用户明确说「只改实现、接口已定」）。

## Phase 0 — Check（盘点）

目标：避免与已有 skill/模块约定冲突，并找出可复用抽象。

1. 读目标路径上的 `AGENTS.md` 与路由命中的模块 skill（不要无脑加载全仓）。
2. 搜索现有同类接口、Mock、gate、测试 helper（按**行为与领域词**搜，不按新名字猜）。
3. 简短列出：
   - 可复用 owner / 接口
   - 必须遵守的 gate / CI
   - 本 feature **非目标**
4. 若用户要求「先看 global skills 有哪些设计-分析-测试逻辑」，先输出盘点表再进 Design。

**Global skills 中与设计/分析/测试相关的现有能力（Check 时可引用，不替代本 skill）：**

| Skill | 角色 | 与本流程关系 |
|-------|------|--------------|
| `plan-interview`（仓库） | 需求访谈 | Design 前需求不清时可先访谈 |
| `design-review`（仓库） | 设计文档 JSON 评审 | Design 产出可送审 |
| `issue-eval` / `new-issue` | 方案评估 / 建 issue | 需要跟踪时挂钩 |
| `zh-rca` / `issue-analyzer` / `log-perf-analyze` | 现象/日志分析 | 仅当 feature 源于故障分析 |
| `use-modern-go`（仓库） | Go 实现 idiom | Impl 写 Go 时必用 |
| `test-debug-fix` | 失败测试迭代修复 | Impl/Test 测挂了再调用 |
| `pr-workflow` / `pr-review` / `review-pr` | PR 与审查 | 验收后开 PR / 审查 |
| `deploy-moi` / 仓库 deploy skills | 环境 | e2e 需要真实栈时 |

本 skill 补上的缺口：**接口文件分离 + Mock 优先 + MVP/边界白话测试设计 + 接口/Gate/叙述协同验收**。

## Phase 1 — Design（需求 → 接口 → MVP）

### 1.1 需求梳理（短、可判定）

用固定骨架，缺证据就标 `待确认`，禁止编造：

```markdown
## 目标
- 用户可观察结果：…
- 成功标准（可测）：…

## 非目标
- …

## 参与者 / 依赖
- …

## 约束
- 性能 / 兼容 / 权限 / 失败语义：…

## 开放问题
- [ ] …（阻塞 / 不阻塞）
```

### 1.2 抽象接口设计（核心）

原则：

- **所有跨边界交互**（IO、存储、RPC、时钟、ID、权限、外部 API）只通过接口。
- **接口单独文件**；实现放在**统一后缀**的代码文件（见命名约定）。
- 接口表达**契约**：输入不变量、输出保证、错误分类、生命周期；不表达某次具体调用细节。
- 业务编排只依赖接口类型，不 `import` 具体实现包（测试同理）。

命名约定（按语言落盘；同包内保持一致）：

| 角色 | Go 示例 | 其他语言类推 |
|------|---------|--------------|
| 接口 | `foo.go` 或 `foo_iface.go`（仅 interface + 契约类型/错误） | `foo.pyi` / `IFoo.ts` |
| 正式实现 | `foo_impl.go` 或领域后缀 `foo_pg.go` / `foo_http.go` | `foo_impl.py` |
| 测试 Mock | `foo_mock_test.go` 或 `internal/testutil/foo_mock.go` | `foo_mock.py` |
| 契约/场景测试 | `foo_contract_test.go`（可对 Mock 与 Impl 共用） | `test_foo_contract.py` |

Go 习惯：小接口、组合；错误用稳定 `reason`/`code` 或哨兵，避免字符串比对当契约。

接口文件顶部用简短注释写清：

- 谁调用、谁实现
- 线程/并发假设
- 幂等与超时
- 禁止事项（例如「实现不得在此回调里起无界 goroutine」）

### 1.3 MVP 白话路径（先于代码）

用**用户/调用方可读的白话文**写一条最小成功路径，不要一上来列函数名：

```markdown
## MVP 路径（白话）
1. 给定 … 前置条件
2. 当 … 发生
3. 系统通过 <接口.方法> 完成 …
4. 则可观察到 …（返回值 / 状态 / 副作用）
5. 失败时调用方能区分 … 并采取 …
```

再从 MVP **展开边界场景表**（仍用白话 + 对应接口断言）：

| ID | 相对 MVP | 场景（白话） | 期望 | 主要断言落在 |
|----|----------|--------------|------|--------------|
| M0 | 主路径 | … | … | Contract / Mock |
| B1 | 缺依赖 | … | … | 错误分类 |
| B2 | 重复调用 | … | 幂等/冲突 | … |
| B3 | 权限拒绝 | … | deny，无副作用 | … |

Design 结束前向用户展示：**接口草案 + MVP + 边界表**。用户否决接口时先改接口，再写测试。

设计文档可选落盘：`docs/plans/plan-NNN-<slug>.md` 或模块既有 design 目录；接口代码本身是一等设计产物（**code as design**）。

## Phase 2 — Impl（测试优先，接口门禁）

顺序不可颠倒：

```text
1) 冻结接口文件
2) 基于接口写 Mock + 契约/场景测试（先绿在 Mock 上）
3) 写正式实现，使同一套契约测试在 Impl 上通过
4) 跑模块 gate / 最小充分静态与单测
5) 需要时再加 e2e：用 Mock 接口实现做灵活回归，真实依赖可标记为集成层
```

### 2.1 Mock 测试优先

- Mock **只实现接口**；行为由测试表驱动（成功、超时、特定错误码、序列调用）。
- 契约测试尽量写成：`runContract(t, dep Factory)`，`Factory` 可返回 Mock 或真实 Impl。
- 编排层 UT：注入 Mock，断言**调用顺序、参数、错误分支、状态迁移**——这些才是有意义的 UT。
- 禁止：只测 getter/setter、只测框架胶水、与接口契约无关的快照、无法说明失败含义的断言。

### 2.2 正式实现

- 实现文件只负责接口承诺；新依赖继续抽象，避免实现里偷偷 new 不可替换的全局。
- 失败语义按项目公开 API 规则细化（可机器识别的 code/reason + 安全用户文案归 owner）。
- Go 改动走仓库 `use-modern-go` list/explain。
- 不扩大范围：不借机重构无关模块。

### 2.3 Gate

在声称「实现完成」之前：

1. 跑**本模块**最小充分测试（契约测试 + 相关包测）。
2. 跑路径命中的本地 gate（i18n、doc、permission、package 等——以仓库 `pr-workflow` / gates-ci 为准）。
3. 记录命令、工作目录、通过/失败；失败则修或降级说明阻塞，**不得**放宽断言装绿。

## Phase 3 — Test（叙述与代码同构）

测试设计是设计的一部分；代码里必须能读到「为什么有这个测试」。

### 3.1 完整表述 MVP case

在测试文件或旁路 `*_test.md` / 测试函数文档字符串中写：

```text
MVP-M0: <一句话>
前置: …
步骤: …
期望: …
保护的接口契约: <Iface.Method> — <不变量>
```

### 3.2 由 MVP 派生边界

每个 `B*` 用例注明：相对 M0 改了哪个条件、多断言了哪条契约。  
没有对应白话场景的测试 = 候选删除或补场景。

### 3.3 测试意义（写在代码里）

每个测试函数（或 table 行）用一行注释回答：

```go
// 意义: 当依赖 X 返回 ErrY 时，编排不得写库且须返回 reason=Z（契约 §2.3）
func TestOrchestrator_DepY_NoSideEffect(t *testing.T) { ... }
```

审查时若读不出「失败了业务上意味着什么」，该测试视为无意义，应改或删。

### 3.4 e2e / 回归

- 默认：用 **Mock 接口实现** 拼出可重复的流程回归（快、稳、可注入故障）。
- 真实依赖 e2e：单独标记，说明环境假设；不阻塞接口契约的日常回归。

---

## Phase 4 — Review（接口 × Mock × Gate）

审查清单（只报有证据的问题）：

1. **交互是否全部经接口？** 实现/测试有无绕过？
2. **接口是否过宽/过窄？** 是否把实现细节漏进签名？
3. **Mock 是否与契约同构？** 有无 Mock 专有分支、生产走不到？
4. **每个测试有无意义注释 + MVP/边界 ID？**
5. **错误与幂等是否可测且已测？**
6. **Gate 是否真实跑过？** 输出是否保留？
7. **非目标是否被实现偷加？**

输出结构：

```markdown
## Review 结论
- 阻塞: …
- 非阻塞: …
- Gate: 命令 → 结果
- 契约覆盖: M0, B1, … / 缺口: …
```

## Phase 5 — 验收

同时满足才算完成：

| 门 | 标准 |
|----|------|
| 接口测试 | 契约测试在 Mock 与（如适用）Impl 上通过；编排 UT 覆盖 MVP+约定边界 |
| Gate | 约定本地 gate 通过或书面阻塞原因 |
| Test 叙述 | MVP 白话完整；边界表与测试 ID 对齐；测试意义可读 |

验收报告模板：

```markdown
## 验收
- 目标: …
- 接口: 路径列表
- MVP: M0 一句话 + 测试名
- 边界: Bi → 测试名
- Gate: …
- 残余风险 / 非目标: …
```

开 PR 时再加载 `pr-workflow`；不要在本 skill 里重写 PR 模板。

---

## 协作与节奏

- **小步交付**：先合接口 + Mock 契约，再合 Impl；便于审查契约本身。
- **用户否决**：改接口优先于堆实现补丁。
- **需求中途变更**：先更新 MVP/边界表与契约测试，再改实现（测试领舞）。
- **多模块**：每个模块自己的接口边界；跨模块只依赖对方公开接口/SDK，不复制 owner 逻辑。

## 反模式

- 先写完 Impl 再补「到点」测试
- 接口与实现塞进同一文件且无法 Mock
- 大而全 God 接口
- 断言内部私有状态却不断言对外契约
- e2e 代替全部单元契约（慢且脆）
- 无人工可理解含义的 UT 刷覆盖率
- 跳过 Design 确认直接大规模改生产路径

## 快速启动话术

用户说「帮我做 feature X」时，默认执行：

1. Check 盘点（相关 skill + 代码内既有接口）
2. 输出需求骨架 + 接口草案 + MVP/边界表（停顿确认，除非用户说继续实现）
3. Mock 契约测试 → Impl → Gate
4. Review + 验收报告
