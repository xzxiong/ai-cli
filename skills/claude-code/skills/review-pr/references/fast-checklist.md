# Fast 模式 — 静态审查 Checklist

仅在用户显式选择 `--fast` 时使用。这是快速、有证据支撑的静态审查，不是完整验证的替代。

## 硬性限制

- 不运行任何测试命令或测试脚本。
- 不触发、重试或等待 CI / 测试任务。
- 不加载 `section-testing.md`，也不产出测试方案 / 覆盖评估。
- 可阅读变更的测试文件或邻近测试代码，仅用于理解变更契约；不得因测试文件存在而推断测试已通过。
- 不得声称已完成测试、CI、运行时或端到端验证。

## 审查优先级

聚焦 diff 与必要周边代码即可高置信度确认的问题：

- 正确性回归、错误路径断裂、不安全的边界处理
- 鉴权 / 授权、密钥、输入校验风险
- API、schema、配置、兼容性破坏
- 无界重试、循环、扇出、资源泄漏、并发隐患
- 新增运行时配置缺少相邻、可长期维护的说明（若 skill 有该强制规则则适用）

跳过穷尽式风格、命名、测试覆盖和推测性架构反馈。报告缺陷前先读周边代码；优先一条可证实问题，而不是多条弱推断。

## 报告结构

```markdown
# Fast Review: <PR title>

PR 基础信息
- **模式**: ⚡ Fast Review（静态审查）
- **测试**: 未执行（`--fast` 模式）

## 〇、总结（TL;DR）
- 一句话概括变更和静态审查结论
- 🔴 / 🟡 / 🟢 发现数量
- 合并建议；若建议合并，必须注明“基于静态审查，测试未执行”
  - **建议合并** — 无 🔴，且明确写出“基于静态审查，测试未执行”
  - **修复后合并** — 有 🔴 必须修改
  - **需要重大修改** — 方案/范围需推倒重来

## 一、关键发现
按严重级别列出有文件/行证据的高信号问题。无问题时明确说明“未发现可从静态审查证实的阻塞问题”。

## 二、审查边界
- 已检查：<diff、相关调用方、配置链路等>
- 未执行：测试、CI 重跑、运行时/E2E 验证
```

每条发现使用主 skill 的 `I-N` 编号，并包含受影响文件/行、影响说明和可操作修复建议。
