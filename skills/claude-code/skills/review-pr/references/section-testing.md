# 2.4 测试方案梳理（UT / BVT / Eval）

---

## T1. 变更 → 测试映射

逐一检查每个新增/修改的**导出函数或核心内部函数**是否有对应 UT：

| 变更函数/方法 | 变更类型 | 覆盖判定 | 对应 UT |
|---------------|----------|----------|---------|
| `pkg.Func()` | 新增 | ✅ / 🟡 / ❌ | `test_func.py::test_xxx` |

## T2. 场景覆盖矩阵（Happy / Unhappy / 反例）

对已有 UT 检查以下维度，**显式区分**三类用例：

| 场景 | 检查项 | 用例类别 |
|------|--------|----------|
| **Happy path**（正常路径） | 正常输入 → 预期输出；典型业务流端到端 | 必备 |
| **Unhappy path**（异常路径） | 各类错误输入 → 正确错误处理；外部依赖失败 → 降级 / 返回错误 | 必备 |
| **反例**（Counter-example / 不应发生） | 非法状态、违反前置条件、越权输入、注入字符 → 被拒绝且不产生副作用 | 强推荐 |
| 边界值 | 空字符串、超长输入、零值、最大值、空 slice/map | 必备 |
| 空值/nil | nil 参数不 panic | 必备 |
| 并发安全 | 多 goroutine 同时调用（如适用） | 视场景 |
| 幂等性 | 重复调用结果一致（如适用） | 视场景 |
| 向后兼容 | 旧版本调用方/旧数据格式 → 不破坏 | 涉及协议/格式变更时必备 |

**关键反问**：
- 每个新增分支是否都有对应 unhappy case？（仅 happy path 覆盖 = 覆盖率假象）
- 是否至少一条用例验证"输入非法时拒绝且不写入任何副作用"？（反例）
- 错误信息是否被断言？（仅断言 `err != nil` 不够，应断言错误类型/关键字）

## T3. Mock 策略

- mock 层级是否正确？（应 mock 外部依赖，不 mock 内部实现）
- mock 返回值是否覆盖成功和失败？
- 是否存在"mock 了一切导致测试只验证了 mock 本身"？
- mock 行为是否与真实依赖一致？

## T4. 测试质量红线

- 是否有有效断言？（禁止只调用不断言）
- 断言是否验证核心业务逻辑（非仅"不报错"）？
- 用例命名是否清晰表达测试意图？
- 是否使用 table-driven tests 覆盖多组输入？（Go 推荐）

## T5. BVT 端到端场景覆盖

| 场景类型 | 检查项 |
|----------|--------|
| 核心正向流程 | 主要业务路径完整走通 |
| 关键分支流程 | 重要条件分支 |
| 错误恢复流程 | 异常输入/依赖故障时的降级 |
| 回归场景 | 历史 bug 的复现路径 |
| 并发场景 | 多请求并发时正确性 |

## T6. 断言质量

- 是否精确验证业务结果（字段值、数据条数、状态码 + 响应体）？
- 是否过度宽松？常见：`status == 200` 不检查 body、`len >= 1` 代替精确值
- 断言失败的错误信息是否足够定位问题？

## T7. 测试数据与环境管理

- 测试数据是否自包含？
- 测试间是否有数据隔离？
- setup/teardown 是否完整？
- 是否依赖特定执行顺序？
- 并发执行安全？

## T8. 回归验证（Bug Fix PR 专项）

- 是否有专门的用例精确复现 bug 触发条件？
- 断言是否直接验证修复效果？
- 修复前失败、修复后通过？

## T9. 故障复现效率（Bug Fix PR 专项）

评估测试用例作为"故障复现工具"的效率：

**复现速度**
- 测试能否在本地秒级/分钟级内复现故障？（理想 < 30s）
- 是否依赖外部服务/特定环境才能触发？（降低效率）
- 是否需要复杂的数据构造或前置步骤？
- CI 中单次运行耗时是否可接受？

**复现精度**
- 测试是否精确命中 bug 的触发条件（最小复现路径）？
- 还是通过大范围 E2E 间接覆盖（可能偶发通过/失败）？
- 如果 bug 回归，这个测试是否 100% 能捕获？

**复现隔离度**
- 测试失败时能否直接定位到具体函数/行？
- 还是需要进一步 debug 才能确认是这个 bug 复发？
- 错误信息是否包含足够上下文（输入值、期望值、实际值）？

**评级标准**：
- ⚡ 高效：本地秒级复现、精确命中、失败即定位
- 🟡 中等：需要特定环境或数据，但基本可靠
- 🐢 低效：依赖外部服务、复现慢、间接覆盖、需二次定位

输出示例：
```
⚡ 高效 — TestInfoExtractDSLStepOrder 直接断言 extract_fields 不含 page_selector，
  本地 <1s，回归即红，错误信息直接指向修复点。

🐢 低效 — TestGoWorker_DocumentParsePageSelectorRealPDFMinerU 依赖外部 MinerU 服务，
  超时 8min，CI 中 MinerU 不可用则 skip。作为 E2E 验证有价值，但不能作为唯一回归门禁。
```

## Eval 方案（涉及 LLM/VLM 时）

- 变更是否影响 AI 输出质量？
- eval 数据集是否充分？
- eval 指标是否明确量化？
- 是否有与 baseline 的回归对比？

**测试补充建议格式**：

```
🧪 测试补充建议：

1. [UT] `pkg.Func()` — 缺少单元测试
   - 建议场景：a. 正常输入 b. 空输入 c. 超大输入
   - 建议 mock：mock XxxClient，分别返回成功/失败/超时
   - 优先级：🔴 必须 / 🟡 建议
```

输出格式：
- ✅ 方案合理 + 理由
- 💡 可优化建议 + 方案 + 预期收益
- 🧪 测试缺陷/缺失 + 补充策略

---

## T10. 测试实现质量

**断言有效性**
- 已有测试是否因本次改动需更新？
- 断言是否验证核心逻辑（非仅副作用/日志）？
- 是否有"永远通过"的断言？

**测试代码 bug**
- expected 值是否正确？（复制粘贴忘改）
- 遗漏 cleanup / teardown？
- 测试中 goroutine 泄漏？
- 错误路径测试是否真触发了错误？

**Flaky 风险**
- timing 依赖（`time.Sleep`/固定超时）？
- ordering 依赖（执行顺序/map 遍历顺序）？
- 环境依赖（特定端口/路径/环境变量）？
- 并发测试竞态？

**可维护性**
- 过度耦合实现细节？
- 大量重复 setup 可提取为 helper？
- 失败错误信息足够定位？

输出：
- ⚠️ 风险 + 位置 + 修复建议
- 🧪 测试问题 + 位置 + 修复建议
- ✅ 已检查无问题的维度

## T11. 测试冗余 / 过度审查（Review 不仅查"不足"，也查"过度"）

**背景**：测试不是越多越好。冗余测试增加 CI 时长、提升维护成本、掩盖真正的覆盖缺口（"100 条测试都在测同一条路径"）。本章节专门识别**过度设计**的测试。

### R1. 重复覆盖同一行为

**识别模式**：
- 多条用例仅输入值不同，但走的是**同一条代码路径**（无新分支触发）
  - 反例：`TestAdd_1+1`、`TestAdd_2+2`、`TestAdd_3+3` 三条用例只是不同数字，无边界意义 → 合并为 table-driven
- 单元测试与集成测试/BVT 重复覆盖同一行为
  - 反例：UT 已经覆盖 `ParseConfig`，BVT 又起一个完整集群只为测同一函数
- mock 了 A 又 mock 了 B，最后断言"A 调了 B"——验证的是 mock 本身，不是业务逻辑

**判定**：
- 🟡 建议合并为 table-driven test
- 🟡 建议删除（已有同级覆盖）

### R2. 测试代码量远超被测代码

**经验值**：测试行数 / 被测行数 > 5:1 时警惕。

- 大量 setup/teardown 模板代码能否提取 helper？
- 是否在用"复制粘贴改一两个值"的方式批量生成用例，而真正变化的只有 1-2 行？→ table-driven
- 是否在为私有/内部小函数写冗长测试，而它已经在导出函数的测试中间接覆盖？

### R3. 过度 mock

- 把所有依赖都 mock 掉，测试只剩"mock 调用验证"，没有真正断言业务结果
- 为纯函数（无外部依赖）写 mock——直接调用即可
- mock 链超过 3 层——信号是被测函数应该拆分

**判定**：
- 🟡 mock 深度 ≥ 3 层 → 建议重构被测函数或减少 mock
- 🔴 测试只验证 mock 被调用，没有验证业务输出 → 必须补充有效断言

### R4. 过度断言

- 一条用例断言 20+ 个字段，但多数是无关紧要的（默认值、内部 ID）→ 失败时无法定位真正问题
- 断言了实现细节（私有字段、内部状态）而非行为契约 → 重构即红，维护成本高
- 对所有字段做 `assert.Equal(expected, actual)`，但 expected 是从被测代码复制粘贴的 → 测试等同于代码复读，无回归价值

**判定**：
- 🟡 断言聚焦行为契约，弱化实现细节
- 🟡 expected 应独立于被测代码推导（硬编码字面量，而非同一份逻辑）

### R5. 过度依赖 E2E / 真实环境

- 一个本可在 UT 层测清楚的分支，被写成了依赖外部服务/集群的 E2E → CI 慢、flaky
- 同一个 bug 在 5 个不同 E2E 场景里都被覆盖 → 保留 1-2 条最关键的，其余删除
- 新增功能对应的 E2E 用例数量，是否匹配功能的实际重要性？

### R6. 冗余的 sleep / retry / Eventually

- `time.Sleep(N)` 写死的等待，多数场景可用 `Eventually` 或同步信号替代
- 超时值远超实际需要（一个 100ms 内完成的操作等了 30s）
- 同一用例内多个 `Eventually` 串联，可以合并

### R7. 一次性脚本被当成长期测试

- 为验证某次 bug fix 临时写的"打印 + 人工观察"型用例，没有断言，留在测试套件里永远 pass
- 调试用的 `t.Log` / `fmt.Println` 大量残留

**判定**：
- 🔴 无断言的用例 → 必须补断言或删除
- 🟡 大量调试用 log → 清理

### T11 输出格式

```
🧹 测试冗余建议：

1. `test_foo.go::TestBar_Case1/2/3` — 三条用例仅参数不同，无新分支
   - 建议：合并为 table-driven，保留 1 条
   - 收益：减少 30 行，CI 快 2s

2. `test_baz.go` — 被测函数 50 行，测试 400 行（8:1）
   - 建议：提取 setup helper；删除重复 mock 验证
   - 收益：可读性显著提升

3. `TestQuux` — 仅断言 `err == nil`，无业务结果验证
   - 等级：🔴 必须补断言或删除
```

**整节结论**：
- ✅ 测试粒度合理，无明显冗余
- 🟡 存在 N 处可精简，建议但不阻塞合并
- 🔴 存在无效/误导性测试（无断言、只验证 mock），必须处理
