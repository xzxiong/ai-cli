# 标准模式 — 完整审查 Checklist

## 全局：设计文档对照

如 Step 2 获取到设计文档，**所有章节**均须对照设计文档审查，不限于 2.1：
- 实现是否与设计意图一致？偏离处标注原因（合理扩展 / 越界 / 遗漏）
- 设计中明确提及的功能是否都已实现？
- 实现中是否包含设计未描述的额外行为？

未获取到设计文档时，基于代码本身推断意图，各章节正常执行。

```
# Code Review: <PR title>

PR 基础信息

## 一、PR 描述评审

  2.0 变更可视化

```

## 〇、总结（TL;DR）

30 秒内让读者掌握全貌：
- 一句话概括 PR 做了什么
- 发现的问题统计（🔴 / 🟡 / 🟢 各多少条）
- 🔴 必须修改的问题摘要列表（来源不限于代码审查，涵盖所有章节）
- PR 描述质量：一句话评价
- 合并建议（三选一，原文必须可被 Step 8 匹配）：
  - **建议合并** — 无 🔴，可 approve
  - **修复后合并** — 有 🔴 必须修改，request changes
  - **需要重大修改** — 方案/范围需推倒重来，request changes

**🔴 问题来源说明**：必须修改的问题可来自任何章节——代码审查（bug/逻辑错误）、方案评审（设计不合理）、测试评审（UT/BVT 不达标、回归复现不充分）、风险检查（安全/并发问题）。只要达到 🔴 级别（不修就不能合并），都列入摘要。

## 一、PR 描述评审

### 设计文档状态

首先标注设计文档获取结果：
- ✅ **已获取设计文档** — 来源：PR body / Issue #xxx / PR comment（一句话概括方案要点）
- ⚠️ **未找到设计文档** — PR body、关联 Issue、PR comments 均未包含方案描述。建议作者补充设计说明。

### PR body 四维评审

对 PR body（及关联 Issue，如有）按四维结构评审：

**背景（Context）**
- 是否清晰描述当前现状和上下文？
- 读者能否仅凭描述理解问题所处的业务/技术场景？

**原因（Why）**
- 是否说明为什么要做？驱动力是什么？
- 问题的严重程度和影响范围是否有数据支撑？

**方案（How）**
- 是否描述了具体的技术方案或实现思路？
- 方案是否足够详细，能指导 Review？
- 是否讨论了备选方案及取舍理由？

**结果（Expected Outcome）**
- 是否明确预期结果和验收标准？
- 是否有可衡量的成功指标？

输出格式：
- ✅ 充分 + 简要说明
- 🟡 不足 + 缺什么 + 建议补充
- 🔴 缺失 + 为什么需要

## 二、方案评审

### 2.0 变更可视化（状态机 / 调用链 / 数据流图）

用图示说明本 PR 实际修改了什么。根据变更性质选择最合适的表达方式：

**选择依据**：
- 状态迁移/生命周期变更 → 状态机图
- 函数调用路径变更 → 调用链图
- 数据在模块间流转方式变更 → 数据流图
- 多种混合 → 选最能体现核心修改的一种，必要时组合

**输出格式**（ASCII 图 + 标注）：

```
修改前（简化）：
A → B → C → D
         ↑ 问题点

修改后：
A → B ──→ D     ← 移除 C 对 B 的依赖
     ↘ C（独立）  ← NEW / ← 修改
```

**标注规则**：
- `← NEW`：新增路径/节点
- `← 修改`：已有节点行为变更
- `← 移除`：删除的路径/节点（用删除线或注释）
- `← 问题点`：修复前的故障位置

**要求**：
- 图必须基于 diff 中实际代码变更绘制，不能是对 PR 描述的复述
- 涉及条件分支时标注分支条件
- 复杂场景可分"修改前"和"修改后"两张图对比

### 2.1 方案合理性

从三个维度综合评估：

**A. 函数调用场景**
- 变更函数在实际调用链中的位置和角色
- 调用方（caller）是否受到影响？是否需要感知此变更？
- 被调用方（callee）的契约是否被破坏？
- 是否有更简洁的实现方式（更少的调用层级、更直接的路径）？
- 是否有可复用的现有组件/库被忽略？

**B. 使用场景覆盖**
- 列出该变更涉及的所有使用场景（正常流、异常流、边界场景）
- 每个场景下方案是否正确处理？
- 是否存在未覆盖的场景会导致回归？
- 向后兼容性：现有调用方在不修改代码的情况下行为是否一致？

**C. 设计决策评审**（重构/链路变更时必填，简单 fix 可跳过）

当 PR 涉及链路重构、算法替换、协议变更等设计决策时，逐条列出关键决策并评估：

| 设计决策 | 旧方案 | 新方案 | 收益 | 引入风险 | 判定 |
|----------|--------|--------|------|----------|------|
| 例：坐标系 | 像素坐标 | 0-1000 归一化 | VLM 输出一致性↑ | 旧 prompt 不兼容 | ✅ 合理 |

评估维度：
- 新方案的收益是否能覆盖引入的风险？
- 是否有更简单的替代方案被忽略？
- 决策之间是否存在矛盾或依赖未理清？
- 删除的旧逻辑是否确定不再有调用方依赖？

输出格式：
- ✅ 合理 + 从哪个维度确认的
- 🟡 存疑 + 具体场景 + 建议验证方式
- 🔴 不合理 + 哪个场景会出问题 + 建议方案

### 2.2 架构评审 / 2.3 存量适配影响

> **条件触发**：满足 SKILL.md「深度开关」条件时 → Read `section-architecture.md` 并按其 checklist 展开。
> 不满足时输出「**2.2/2.3 不适用**（本 PR 无架构重构或存量破坏性变更）」跳过。

### 2.4 测试方案梳理

> Read `section-testing.md` 并按其 checklist 展开（含 T1-T10 测试充分性 + T11 测试冗余审查）。

### 2.5 是否真正解决问题（Goal-Result 对齐）

**核心问题**：本 PR 是否真的能解决它在 PR body / Issue / 设计文档中声称要解决的问题？

这一节不是问"代码写得对不对"（那是第四节），而是问"**事情做对了吗**"。一个 PR 可以代码全对、测试全过，但并没有解决问题。

#### 评审步骤

1. **重述问题**（1-2 句）
   - PR body / Issue 中要解决的问题是什么？用自己的话写出来
   - 如果作者没说清楚，从 diff 反推，标注「⚠️ PR 目的需读者自行推断」

2. **追溯因果链**
   - 从问题症状 → 根因 → 本 PR 改动 → 预期效果，是否闭环？
   - 反例：Issue 报"接口慢"，PR 改了一处日志格式 → 没有闭环
   - 反例：Issue 报"租户越权"，PR 加了校验但只覆盖了 3 条路径中的 1 条 → 闭环不完整

3. **覆盖问题边界**
   - 问题是否有多条触发路径？本 PR 是否覆盖了全部？
   - 问题是否可能在其他模块以同样模式存在？是否需要顺手修复（或标注 follow-up）？

4. **验证修复有效性**
   - 是否有回归测试精确复现 issue 描述的场景？（对照 section-testing.md T8）
   - 修复后的行为是否被某种方式验证过（UT / BVT / 手动测试记录）？
   - 如果 PR 是「优化」性质：是否有量化指标（benchmark / 耗时对比）支撑？

5. **是否引入了新的问题**
   - 解决一个问题的同时是否破坏了另一个场景？（回归）
   - 是否把问题从一个模块转移到另一个模块？（治标）

#### 输出格式

```
✅ **完全解决** — PR 改动与 Issue 根因对应，回归测试已覆盖原症状
🟡 **部分解决** — 闭环存在但边界未覆盖（如 3 条触发路径只覆盖 1 条），建议作者补充或标注 follow-up
🔴 **未解决 / 偏离** — 改动与问题根因脱节，或修复方案未经验证
⚠️ **PR 目的不清** — PR body / Issue 均未描述问题，无法判断 Goal-Result 对齐
```

**对本节结论的处理**：
- ✅ 完全解决 → 继续后续章节
- 🟡 部分解决 → 在合并建议中提示"建议作者补充 X"
- 🔴 未解决 / 偏离 → 合并建议至少为「修复后合并」或「需要重大修改」，与代码质量无关

2-3 段话概述：
- PR 的背景和目的
- 核心变更内容（按模块分组）
- 影响范围

## 四、代码审查（逐文件）

对每个变更文件审查：
- 代码正确性：逻辑错误、边界条件、空指针、类型安全
- 代码风格：命名规范、函数长度、注释质量
- 错误处理：遗漏处理、错误信息清晰度
- 可维护性：代码重复、魔法数字、硬编码
- 测试覆盖：关键路径是否有测试

输出格式：
- 🔴 **必须修改**：bug 或严重问题
- 🟡 **建议修改**：质量或可维护性
- 🟢 **可选优化**：锦上添花

每条包含：
```
<a id="issue-N"></a>
**🔴/🟡/🟢 I-N** — `<file_path>` L<line>
问题：<description>
建议：<suggestion / code example>
```

> ⚠️ 使用 `I-N` 编号（如 `I-1`），**不要**使用 `#N`。GitHub 会将 `#数字` 自动解析为 issue/PR 链接。

## 4.5、API / 配置变更清单

当 PR 涉及对外 API、配置、Schema 变更时列出（无则省略本章）：

| 类型 | 变更项 | 变更内容 | 向后兼容 | 备注 |
|------|--------|----------|----------|------|
| API | `endpoint` | 新增/删改 | ✅/⚠️/🔴 | 迁移指引 |
| 配置 | `config_key` | 默认值变更 | ✅ | 生效范围 |
| Schema | `ModelName` | 新增字段 | ✅ | 内部使用 |

检查范围：
- API 接口变更（HTTP/gRPC/WorkItem）
- 请求/响应字段增删改
- 配置项变更（YAML/环境变量/Feature Flag）
- 数据库/消息 schema 变更
- 依赖变更

---

## 4.6、数据访问 / SQL 专项审查

> **条件触发**：diff 中含 SQL / ORM 调用 / 事务 / migration / 权限 DDL 任一信号 → Read `section-data-access.md` 展开 D1-D7 审查。
> 不满足时输出「**4.6 不适用**（本 PR 无数据访问变更）」跳过。

**审查维度速览**（详见 `section-data-access.md`）：
- **D1 SQL 必要性**：是否存在不必要/冗余/可合并的 SQL
- **D2 N+1 检测**：循环内查询 / 写入 / 更新
- **D3 SQL 效率**：SELECT *、索引失效、缺 LIMIT、深翻页
- **D4 权限 / 越权**：参数化查询、租户隔离、权限变更审计
- **D5 事务边界**：最小化、锁、MatrixOne RC 隔离级别陷阱
- **D6 Migration / DDL**：索引并发、列默认值、回滚
- **D7 读写一致性**：写后即读、缓存一致性
